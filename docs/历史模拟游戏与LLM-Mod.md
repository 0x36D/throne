不过 Bannerlord 的问题恰好与 Victoria 3 相反：它有很强的人物世界和很开放的 C# mod 接口，却没有足够细致的国家行政、财政、人口、法律和官僚模拟。也就是说，把 LLM 接进去很容易，但是你首先得自己造“国家”这一层。因此如果你想做的是“一个封建领主与封臣、地方贵族、军队和城镇之间的政治”，Bannerlord 是很合适的实验平台；如果你要模拟 19 世纪或现代官僚国家，就需要自己添加非常多系统。

RimWorld 则是另一个非常值得研究的技术参照物。它不是历史模拟，但它可能是现在最适合研究“LLM agent 如何嵌入 simulation game”的现成生态之一。RimWorld 本身是 C# 游戏，Harmony 可以在运行时 patch 游戏方法，这也是 RimWorld mod 常用的做法。([边缘世界百科全书](https://rimworldwiki.com/wiki/Modding_Tutorials/Harmony?utm_source=chatgpt.com)) 目前已经有 RimTalk 这样的框架，会把人物情绪、trait、关系和当前情况组合成上下文，调用 OpenAI-compatible、Gemini 或本地模型生成对话，并且提供公开 API 让其他 mod 添加上下文和变量。([GitHub](https://github.com/jlibrary/RimTalk/blob/main/README.md?utm_source=chatgpt.com)) 更进一步，RimMind 这类项目已经开始把 LLM 拆成 Personality、Memory、Dialogue、Actions、Advisor、Storyteller 等模块，让 AI 不只是“说话”，还能够做工作决策和选择事件。([GitHub](https://github.com/RimWorld-RimMind-Mod/RimWorld-RimMind-Mod-Bridge-RimTalk/?utm_source=chatgpt.com)) 如果你真正准备开发，我会强烈建议研究这些项目的架构，即使最后一行 RimWorld 代码都不用。

这里有一个我认为非常重要的设计分界。你说“多方权力结构，用 LLM 做角色扮演可能效果更好”，这件事我基本赞同，但最好把“权力”和“角色扮演”拆开。假设财政部长告诉你：“今年粮食产量预计增长 8%，完全不必担心饥荒。”游戏真正的粮食产量不应该由 LLM 决定，也不应该让 LLM自己编一个数字。模拟器内部可能知道真实增长是 -3%；部长只能访问农业部报表，而农业部数据存在两个月延迟；地方官为了考核已经虚报了粮食产量；部长本人又属于某个政治派系，不希望总统停止出口粮食。系统先根据这些客观条件生成部长能够知道的“观察值”，然后 LLM 根据他的知识、利益、人格和记忆决定如何向你解释这个观察值。这样产生的谎言是“模拟出来的谎言”，而不是模型 hallucination。

同样，当你说“命令财政部提高地方教育拨款”时，也不应该让 LLM直接回答“好的，我执行了”。比较理想的结构是玩家提出一个政治意图，比如把农村教育预算提高 20%；财政部长 LLM 可以支持、讨价还价或者反对，但真正进入游戏世界的是一个结构化的 PolicyProposal。之后议会、财政部门、教育部门、地方政府分别根据自己的权限、资源、偏好和制度规则处理它。最后真正落实的可能只有 11%，半年以后中央收到的报告却说完成了 18%。LLM负责解释“为什么只完成了这些”“谁把责任推给谁”“谁在暗中阻挠”，而真正完成了多少由 simulation engine 算出来。

这样一来，LLM 特别适合处理传统游戏最昂贵的部分：政治人物的语言、理由、谈判、结盟、威胁、妥协以及对事件的主观解释。而传统代码特别适合处理 LLM 最不可靠的部分：账本、人口、预算、资源约束、组织权限、执行结果和因果关系。两者结合之后，你会得到一个很有意思的结构：游戏拥有一个不可直接查看的 objective world state；每个 actor 拥有自己的 observation state；每个 actor 还有 beliefs，也就是他认为世界是什么样子；玩家看到的其实只是这些 actor 发来的 reports。这样“情报”本身就成了游戏机制。

所以如果你的目标是先验证玩法，我不会建议一开始从头写一个完整历史大战略游戏。最有效的实验路线其实是做一个非常小的“政权模拟器”：一个国家、五到十个权力中心，例如财政部、军队、地方总督、地主、商人、宗教机构和议会；几十个真实状态变量；几条信息渠道；几种政策；然后让几个 LLM agent 担任关键人物。玩家每个月只能收到内阁报告和少量统计数据，通过谈话、任命、调查和政策来影响局面。只要这个系统能产生类似“财政部长告诉你预算没问题，但地方政府正在拖欠教师工资，而内务部长刻意没有向你报告抗议”的局面，你的核心游戏已经成立了，地图和几千个 POP 都可以以后再加。

如果想直接以现成游戏做 proof of concept，我会这样选：想验证“政治制度和利益集团”，用 Victoria 3 做纯脚本 mod；想验证“个人权力网络＋LLM”，用 Bannerlord 做 C# mod；想研究成熟的 LLM-agent 游戏架构，直接拆 RimWorld 的 RimTalk/RimMind 源码；想实现你完整的“国家不是玩家的身体、信息不是事实、命令不是结果”这一理念，最终独立开发反而很可能是最干净的路线。Paradox 游戏尤其适合拿来验证第一部分，却因为脚本沙箱不能直接访问操作系统而不太适合作为最终的 LLM runtime；Bannerlord 则几乎正好相反。

如果把它进一步收敛成一个具体游戏，我甚至认为你的核心 UI 不应该是一张铺满准确数字的 Victoria 式国家面板，而应该是一张办公桌：预算报告、情报简报、地方电报、部长备忘录、报纸、私人信件和会议记录。玩家看到的任何数字都必须有“来源”，不同来源可以互相矛盾。玩家真正的资源也就不再只是金钱和政治点数，而是“谁愿意告诉我真话”“谁有能力把我的意志贯彻到县一级”“我是否有另一个机构能够核实他的报告”。这会把传统大战略游戏里几乎不存在的一个东西变成最重要的资源：国家能力本身。

从开发角度，我认为这里真正值得做的不是“让 GPT 扮演维多利亚时代的部长”，而是建立一个明确的 agent protocol，例如每个角色每回合只接收 `observations + memories + goals + relationships + institutional powers`，只能返回诸如 `message / proposal / vote / order / conceal / investigate` 之类严格定义的动作；所有动作再由确定性的 simulation engine 解析。这样以后模型可以随便换，甚至可以让次要 NPC 使用传统 utility AI，只让十几个关键人物调用 LLM，成本和稳定性都会好很多。

如果你愿意继续把这个想法往“真的可以做”的方向推进，我可以下一步直接帮你设计一个最小可玩的原型，包括国家真实状态、角色认知状态、权力机构、命令执行链、信息失真机制以及 LLM 的输入输出 schema，并分别给出“Bannerlord Mod 版”和“独立游戏版”的技术架构。

# chatgpt response

可行，而且我认为这条路比“预先穷举所有玩家可能做的动作”更有潜力，但前提是不要把 coding agent 理解成“游戏运行时随时可以修改 engine 源码的 AI 程序员”。如果真让它直接改核心代码、热加载、继续跑模拟，系统会迅速失去可验证性：同一存档在不同时间可能产生不同规则，agent 写出的函数可能破坏状态不变量，旧存档可能无法读取，甚至一个普通的角色请求就可能间接获得文件系统、网络或者宿主进程权限。更合适的思路是把 engine 分成一个很小而且不可由 agent 修改的“内核”，以及一个可以由 coding agent 动态扩展的“规则层”。coding agent 不是修改游戏世界的神，而是在一个严格受控的扩展环境里为世界增加新的可调用能力。

例如玩家作为皇帝突然说：“命令户部调查过去五年各省盐税账目，并把地方账册和中央记录交叉核对。”开发者事先可能根本没写一个 `investigate_salt_tax_records()` 函数。普通 LLM agent 如果只有固定工具列表，只能回答“没有这个能力”。你设想的 coding agent 则可以发现现有底层 primitive 已经包括“查询地方财政记录”“查询中央税收记录”“按照行政区遍历”“比较数据”“创建调查报告”“消耗官僚资源”等，于是它编写一个新的复合操作，把这些能力组合起来。测试通过之后，这个操作被注册为一个新的 capability。以后皇帝、审计院甚至地方官都可能使用它。这实际上是在运行过程中逐渐扩展游戏的“制度词汇”。

这里最关键的区分是“创造新函数”和“创造新物理规律”。前者可以非常开放，后者应该非常谨慎。比如 coding agent 可以创建“全国盐税稽核”这种新行政程序，因为它最终仍然只是调用既有的财政、人员、时间、信息和权限系统；但它不能因为玩家说“让财政部偷偷多印一点钱”就直接写一个函数把国库变量加一百万。增加货币必须通过 engine 已定义的货币发行、资产负债、通胀和权限机制。如果不存在这样的 primitive，那么 coding agent 应该得到的结论是“当前世界模型没有足够的机制表达这个行为”，而不是临时写一个作弊函数。这条界线决定了系统最终是一个 simulation，还是一个不断即兴编故事的 LLM playground。

因此我会把整个游戏架构设计成三层。最底层是 simulation kernel，管理时间、实体、账本、产权、人口、资源、权限、因果事件和随机数。这一层最好尽可能确定性，而且不能让 coding agent 动态修改。中间是 capability runtime，它暴露大量比较细粒度但安全的原语，例如 `transfer_budget`、`appoint_official`、`request_report`、`inspect_region`、`issue_order`、`seize_asset`、`move_unit`、`create_committee`、`schedule_event`。最上层才是 agent layer，包括扮演人物的 LLM 和负责扩展能力的 coding agent。人物 agent 发现当前工具不足时，不应该自己写代码，而是提交一个“能力缺口”，由专门的 coding agent 处理。

这个 coding agent 最好也不要拥有无限自由，而是工作在一个非常类似插件 SDK 的环境里。它能够看到 API 文档、状态 schema、允许调用的 primitive、几个相关测试以及当前需求，但看不到 engine 私有实现，也不能访问宿主文件系统、网络、shell、数据库连接或者任意反射接口。技术上可以使用受限 Lua、WASM、某种 DSL，或者经过强约束的 C#/Rust/Python 子集。实际做产品时，我反而很看好 WASM 或自定义 DSL，因为你真正需要的是一个“能够组合规则”的环境，而不是让 agent 拿到完整编程语言。完整 Python 或 C# 虽然原型非常方便，但安全边界会复杂得多。

生成代码以后也绝不能立刻执行。我会要求它经过至少三个阶段。第一阶段是静态验证，检查它引用的所有 API 是否存在、是否访问了禁止资源、是否可能越过权限边界。第二阶段是 simulation tests，也就是在一个复制出来的世界状态上运行，例如这个新操作是否守恒货币、是否会产生非法负人口、是否能够在有限时间内终止、是否只修改声明过的状态。第三阶段则是 property tests，即检查整个世界永远应该满足的不变量，例如人物不能同时存在于两个地点，国库变化必须对应至少一个账本分录，死亡人物不能发布命令，地方官不能调用中央皇帝权限。只有全部通过以后，新 capability 才能进入正式世界。

而且最好不是“agent 写了什么就永久加入什么”。每个动态能力都应该有一份 manifest，其中记录名称、版本、作者 agent、创建原因、允许读取的状态、允许写入的状态、依赖的 primitive、权限要求、资源成本、测试集以及代码哈希。于是你的存档实际上不仅保存世界状态，还保存这个世界曾经演化出来的制度代码。如果五十年后这个国家发明了一套特殊的粮食征收制度，存档会包含它的 capability 定义。这样不同世界甚至会长出不同的“制度软件”。

这个机制和你前面提到的政治模拟结合起来会非常有意思，因为 coding agent 并不一定只是一个开发工具，它甚至可以成为游戏世界的一部分。例如皇帝要求建立一个“巡抚考成制度”，现实世界中这不是一个简单按钮，而是一套制度设计。游戏可以首先让大臣 agent 讨论方案，然后由 coding agent 把最终方案编译成规则：哪些地方官需要提交哪些数据，以什么频率提交，考核标准是什么，谁有权审计，造假被发现会发生什么，运行这套制度需要多少官员。玩家实际上在“编程自己的国家”，但使用的是政治语言而不是代码。这会非常符合你前面那种国家能力模拟的方向。

进一步讲，甚至可以把“法律”本身设计成一种程序。传统游戏里的法律通常只是几个 modifier，例如“土地税 +10%，地主满意度 -5”。但真实法律往往是一套 procedure。谁负责执行、谁负责监督、谁可以申诉、什么情况属于例外、谁承担成本，都决定法律实际效果。你的 coding agent 可以把自然语言制定的制度转成受控的 executable policy。于是一次政治改革不只是改变变量，而是真的生成一段新的国家运行逻辑。这可能是整个设计最有潜力的部分。

但是有一个很重要的工程原则：coding agent 最好永远不能自己增加新的 primitive。它只能组合开发者定义的 primitive。如果它发现缺一个关键底层能力，比如整个 engine 没有“债务”概念，它应该生成一个 `CapabilityGap`，告诉开发者或者更高权限的离线开发 agent：“要实现政府债券，需要增加 debt instrument primitive。”真正修改 simulation kernel 的工作最好发生在游戏版本更新时，而不是某个玩家的运行时会话里。否则一旦 agent 可以自己定义底层语义，整个系统就没有真正意义上的边界了。

我甚至会给 coding agent 设计一种非常强的“预算制度”。它每次创建代码都有 complexity budget，例如最多调用多少种 primitive、最多创建多少持久状态、每 tick 最多运行多少计算、最多影响多少实体。复杂操作应该自动变成异步流程，而不是一个巨大函数瞬间完成。比如“全国人口普查”不能一次遍历一亿人口直接得出真实数字，而应该生成调查任务，消耗调查员、预算和时间，逐地区收集带误差的数据。这样 coding agent 即使在增加新能力，也无法绕过你最核心的“信息与行政能力有限”这个游戏原则。

这里还会出现一个很值得利用的效果：coding agent 本身可以犯“工程错误”，但最好不要让这种错误表现为 Python exception 或游戏崩溃，而是把它转译成制度失败。比如某套新税制算法设计得过于复杂，地方官僚能力不够，那么 simulation engine 可以表现为执行积压、报表错误、腐败机会增加，而不是简单报错。换句话说，agent 写出来的是一个逻辑上合法的制度，但制度实际运行得好不好仍然取决于游戏世界。这样“国家制度设计”和“国家能力”才真正联系起来。

从安全管理角度，我会让所有动态代码都运行在一个 transaction 里。函数开始运行前记录允许修改的状态范围；执行过程中所有修改进入临时 journal；运行结束以后 engine 检查 invariants；只有验证通过才 commit。如果出错、超时或者违反规则，就 rollback。这样 coding agent 即使产生了 bug，也最多导致某项政策执行失败，而不是损坏整个存档。这种模式其实很像数据库事务，也很适合 simulation game。

另一个非常重要的机制是 replay。一个历史模拟游戏如果大量使用 LLM 和动态代码，调试会极其困难，所以所有 agent 输入、agent 输出、生成代码、随机种子、tool invocation 和 state mutation 最好都记录成 event log。理论上，你应该能够从 1836 年 1 月 1 日的存档一路 replay 到 1848 年革命，并准确回答：“为什么这里爆发了革命？”系统能够追踪到某次地方粮食调查、某个官员虚报、某项动态生成的粮价管制规则以及之后的一系列决策。这不仅方便开发者调试，也可能成为游戏本身的一部分——历史学家、监察官甚至玩家都可以事后调查发生过什么。

所以我会把 coding agent 的身份定位成“动态制度编译器”，而不是“拥有 repo write access 的 Copilot”。人物 LLM 负责提出目标和进行政治互动，coding agent 负责把新的制度或复杂行动转成受限程序，simulation kernel 负责决定现实到底发生什么。三者之间的权限应该是严格单向的：角色可以请求能力，coding agent 可以组合能力，而只有 kernel 可以改变世界真相。

如果这样设计，你其实会得到一个很罕见的游戏结构：传统游戏的“动作空间”是开发者事先写死的，而你的动作空间可以在运行时生长；但是世界规则仍然保持稳定。玩家不是在有限菜单中选择行为，而是在自然语言中发明新的行政制度、组织和工作流程。真正有趣的地方可能最终甚至不是“LLM NPC 很像真人”，而是每一个长期运行的国家都会逐渐积累一套自己独有的、由历史事件塑造出来的制度代码。这一点我认为比单纯让 NPC 接 GPT 更有创新价值。

要更接近真实世界，最关键的一步是把“国家秩序”从 engine 的前提改成 simulation 的结果。也就是说，不能假设世界里天然存在一个稳定的“政府对象”，它永远拥有合法命令权、税收权、军队控制权和领土主权，然后所有政治都只是发生在这个对象内部。真实历史里，这些权力本身就是可争夺、可分裂、可转移、可伪造的。皇帝名义上还在位，并不意味着他真的控制禁军；中央政府仍然存在，也不意味着地方会交税；法律仍然有效，也不意味着法官、军官和地方官还愿意承认它。换句话说，engine 不应该把“谁统治国家”保存成一个单一字段，而应该把统治拆成很多实际关系，并允许这些关系逐渐脱钩。

比较合适的底层模型，是把政治秩序表示为一张不断变化的“控制与承认网络”。任何政治行动者，无论是君主、首相、军阀、军队司令、地方总督、宗族、农民组织、商会还是革命委员会，都可以分别拥有不同程度的财政控制、武装控制、官僚控制、信息控制、司法控制、交通控制和象征性合法性。一个皇帝可能仍然拥有极高的礼仪和法统地位，但无法任命军官；一个权臣可能没有正式头衔，却控制宫门、禁军和诏书流转；一个地方总督可能继续在文书里称臣，但已经截留税收、独立任命官员和扩军。这样一来，“架空”就不需要设计成一个特殊事件，它只是某些控制边逐渐转移后的自然结果。

这也意味着 engine 里最好不要有一个不可侵犯的 `sovereign_id`。可以有“谁被法律文本称为君主”“谁的命令被哪些机构承认”“谁能够实际强制执行命令”“谁掌握国家印玺”“谁控制首都”“谁能支付军饷”这些彼此独立的状态。大多数和平时期，它们会高度重合，于是玩家感觉自己就是国家；危机时它们开始分裂，玩家才会发现原来“我是皇帝”与“我能让别人服从”是两回事。这个设计会直接解决权臣架空的问题，而且远比一个“摄政度 73%”的抽象数值真实。

政变也应该从“事件”变成一种普通但高风险的协调行动。政变成功的核心并不是某个人按下“发动政变”按钮，而是几个关键节点在极短时间内同时改变服从对象：宫廷卫队是否放行，首都驻军是否响应，通讯机构是否封锁消息，财政部门是否继续发薪，官僚系统是否接受新命令，广播或诏书系统是否认可新的权威。因此可以把政变模拟成一种 coordination problem。某个密谋者需要秘密获得关键角色的承诺，而承诺本身可能不可靠；参与者只能看到局部信息，也不知道其他人是否会在关键时刻倒戈。当行动开始后，各节点根据自己的利益、恐惧、认知和眼前局势重新决定服从谁。这样政变有时会瞬间成功，有时会失败，有时最有趣的是失败一半：首都被控制，但外省拒绝承认，于是政变自然演化成内战。

弑君也不应该简单理解成“角色死亡”。它真正重要的是死亡之后权力网络如何重新连接。如果政治体系已经高度制度化，君主死亡可能只触发正常继承；如果整个秩序依赖个人效忠，那么同一次暗杀可以让国家立即碎裂。因此角色死亡对政治系统的冲击，应该取决于该角色承担了多少“桥接关系”。一个高度个人化政权里，大量军队、官员、地方势力可能不是效忠抽象国家，而是效忠某个人；这个人一死，所有相关承诺都要重新计算。这样同样是“刺杀统治者”，在不同政体中会出现完全不同的结果，而且这种差异来自系统结构而不是预写剧情。

农民起义则要求你进一步放弃另一个传统游戏假设：只有正式政治角色才能成为政治主体。最好把人口组织能力也模拟出来。普通人口最初可能只是分散的家庭、村社、宗族、教团和行业网络，但在某些条件下，这些网络可以产生新的 collective actor。饥荒、征税、征兵、宗教传播、地方暴力和国家镇压并不会直接增加一个叫“叛乱度”的数字，而是改变信任关系、共同认知、组织网络、资源获取和风险判断。当足够多的人相信“别人也会反抗”时，潜在不满才会转化成集体行动。这一点很重要，因为历史上很多起义的关键并不只是大家有多不满，而是大家是否相信其他人也会一起行动。

这里可以引入一个非常有用的概念：政治秩序是一种 equilibrium，而不是 rule。和平时期之所以稳定，不是因为 engine 宣布“现在处于和平状态”，而是因为绝大多数人预计别人会继续服从现存秩序，所以自己也选择服从。一旦这种共同预期崩溃，系统可以发生极快的非线性变化。比如连续几个月欠饷本身未必导致军队叛变，但如果某个军团率先拒绝命令，而其他军团得知中央已经无法惩罚它，那么服从 equilibrium 可能突然塌陷。这种模型才能产生历史上那种看起来“昨天还正常，几天后整个政权已经瓦解”的现象。

从 engine 设计上，我会进一步把“法律权限”和“实际能力”完全分离。任何 actor 都可以尝试任何物理上可表达的行为，但结果取决于他能动员什么。例如一个没有法律权限的将军仍然可以命令部队逮捕首相；engine 不应该回答“你没有权限执行这个操作”，而应该回答“你发出了这道命令”。随后部队决定是否服从，警察是否抵抗，法院是否承认，其他将军如何反应。传统软件系统里的 authorization 通常是硬门槛，但政治模拟里的 authorization 很多时候只是一个影响服从概率和后续合法性的变量。真正的硬限制应该是物理能力，例如你不能调动一支与你完全没有通讯渠道、没有指挥关系、也没有任何影响力的军队。

这会让之前讨论的 coding agent 也需要重新定义。它不能只生成“合法制度内部的新流程”，还应该能够生成非常规行动计划，但它仍然不能修改底层物理规律。比如一个权臣说“我想绕过皇帝，以中书省名义向地方下令”，coding agent 可以组合“伪造或截取文书”“调用已有官僚通信网络”“利用印玺权限”“隐藏真实来源”等 primitive，形成一个新的 operation。但它不能直接写 `set_ruler(self)`。同样，一个革命组织可以创建地下征税、秘密通信、武装招募、宣传网络等新制度。这些制度在形式上和国家制度没有本质区别，只是它们的合法性来源、公开程度和强制能力不同。

进一步说，我甚至不会在 engine 里把“国家”和“叛军”定义成完全不同的实体类型。它们应该使用同一套组织模型。一个国家拥有财政、武装、行政网络和合法性；一个成熟的叛乱组织也一样。区别只是规模、承认范围和制度成熟度。这样农民军占领三个县以后，可以逐渐开始征粮、任命地方官、审判犯罪、发行文告；如果继续扩张，它就自然变成一个竞争政权。反过来，一个中央政府如果逐渐失去财政、军队和地方行政控制，也可能只剩下一个被国际承认的“合法政府”。这种对称性非常重要，因为它避免了很多策略游戏常见的问题：反叛者在成功前只是一个特殊 debuff，成功以后突然凭空变成完整国家。

玩家身份也必须因此改变。最有意思的设计可能是：玩家不是永远绑定在“国家”上，而是绑定在一个人物、家族、派系，或者更抽象的政治主体上。如果玩家是皇帝，被政变后，他可能还活着，但已经被软禁，那么游戏并不结束；你突然从国家最高统治者变成一个拥有残余合法性、人脉和潜在支持者的囚徒。你可以尝试联系旧臣、策反禁军、寻求外国支持或接受退位。这样“失去政权”就不等于 game over，而是政治状态发生转变。对于你想模拟的世界，这一点几乎是必要的，否则 engine 最终还是会偷偷把“玩家”和“国家”绑定起来。

信息系统在这种危机里也会变得尤其重要。政变发生时，玩家不应该立刻看到“第 3 军已倒戈，首都控制度 42%”。你可能只收到互相冲突的报告：“城南有枪声”“禁军宣称仍效忠陛下”“首相失踪”“电报局停止回复”。甚至某个机构是否仍然属于你，本身就是未知状态。engine 有真实状态，但玩家和每个 actor 只有自己的 belief state。实际上，当秩序开始瓦解时，“谁认为谁掌权”本身就会反过来影响谁真正掌权。这是一个很适合 LLM 的区域，因为角色需要根据不完整、矛盾甚至蓄意伪造的信息做判断，而这种判断又会进一步改变世界。

最终你可以得到一种很强的涌现效果：不是 engine 随机掷骰子说“发生宫廷政变”，而是财政危机导致军饷拖欠，皇帝试图裁撤禁军，禁军统领开始与首相秘密结盟，情报机构负责人为了自保隐瞒消息，一名地方将军误以为皇帝已经死亡，因此宣布支持“临时摄政委员会”，这个消息又让其他地方势力改变判断，最终整个秩序坍塌。事后玩家可以把所有 event log 打开，发现没有任何一步叫“触发政变事件”，但整体结果就是一次完全可信的政变。

如果把这个思路概括成一句 engine 设计原则，就是：不要模拟“秩序中的政治”，而要模拟“秩序本身如何被持续生产”。法律、国家、王位、军队效忠、官僚服从、货币信用甚至领土边界，都不应该是不可变的背景常量，而应该是大量 actor 每天不断重复、承认、执行之后暂时稳定下来的结果。只要 engine 能做到这一点，政变、革命、架空、分裂和改朝换代就不再需要作为特殊系统一项项添加，它们会成为同一个底层模型在不同条件下自然出现的状态。

`sim-api` 是世界与 Agent 之间唯一的门。它提供诸如“发命令”“请求报告”“与某人通信”“调动资源”“调查某机构”这样的 primitive，而且严格检查一个 actor 实际拥有的渠道和能力。

`event-store` 保存所有客观世界事件。这个日志与 Harness 自己的 agent session log 分开。前者记录“真实发生了什么”，后者记录“某个人知道了什么、相信了什么、为什么采取行动”。这两个日志同时存在非常重要，因为以后你就可以重建“真实历史”和“人物眼中的历史”。

`client` 最初只是一个浏览器界面。玩家看到的是报告、信件、地图、人物关系和有限统计，而不是数据库后台真实值。

这样做有一个很大的好处：将来 DeepSeek Harness 如果不好用，你可以整个换掉。比如将 Agent Runtime 换成其他框架，甚至某些重要人物用 GPT、某些用 DeepSeek、某些完全不用 LLM，simulation core 都不用改。反过来，如果以后想把 Web UI 换成 Godot，也只是更换 client。这个解耦对你的项目尤其重要。

至于有没有比 DeepSeek Harness 更好的现成“游戏 simulation engine”，我的判断反而是没有必要找。你的 simulation core 本身其实没有想象中庞大。我们讨论了很多复杂政治现象，但如果设计得对，它们并不是几十个独立系统，而是几个统一 primitive 的组合。例如政变、军阀割据、正常政府更替，本质上都是“actor 对组织和资源的控制关系发生变化”；谣言、情报误差、地方虚报，本质上都是“objective state → observation → belief”的转换；法令、政变命令、革命号召本质上都是 actor 向其他 actor 发出的 intent，接收者根据自身状态选择响应。统一以后，底层数据模型其实可能只有十几个核心概念。

所以如果由我给 Codex 下第一个工程任务，我不会说“做一个历史模拟游戏”。我会让它先做一个极小的 headless simulator：只有一个国家、一个皇帝、五个大臣、三个地方总督、三支军队、十个地区、一套财政系统和一个月度 tick。没有漂亮 UI，没有地图动画。首先证明四件事情：玩家收到的信息可以与真实世界状态不同；命令可以经过组织链产生部分执行和扭曲；角色可以自主改变效忠关系；中央政府可以在没有预设“政变事件”的情况下自然失去实际控制权。只要这四件事情成立，我们的 engine 基本思想就成立了。

然后第二阶段再接 DeepSeek Harness。先只让三四个关键人物使用 LLM，其他几百个角色继续使用普通 utility AI。这样可以非常清楚地比较“LLM 到底增加了什么”，也避免刚开始就面对调用成本、延迟和上下文管理的问题。等这部分稳定以后，再加入 coding agent，让它第一次完成类似“玩家提出建立一个此前不存在的地方巡查制度 → coding agent 组合已有 primitives → sandbox 测试 → engine 注册新 capability”的完整闭环。

我尤其不建议第一版就让 coding agent 修改整个 repo。开发阶段的 Codex当然可以修改项目代码；但是进入游戏以后，游戏世界里的 coding agent 应该只拥有专门的 sandbox 和 SDK。这两个“coding agent”虽然都可能用同一个模型，但身份必须完全不同。外面的 Codex 是开发者，拥有 repo 权限；里面的 Agent 是游戏机制，只能操作经过限制的 capability language。否则一次游戏里的新税法有 bug，可能直接把整个程序改坏。

因此，如果你现在真的准备开始，我的建议可以压缩成一句话：Simulation Core 从头写；Agent infrastructure 不从头写，用 DeepSeek Harness；UI 第一版用 Web；Codex作为项目开发者来搭整个 repo；游戏内部的 coding agent 后续再作为受限系统加入。

这个组合的风险比“整个东西完全从零”低很多，又不会被某个现成游戏引擎或 DeepSeek Harness 的抽象反过来限制我们。DeepSeek Harness 本身是 MIT 开源，而且明确就是为“自己重新组合 agent runtime”这种使用方式设计的，所以在架构理念上确实是目前我看到与这个项目最吻合的候选之一。([DeepSeek](https://www.deepseek.com/harness/en/?utm_source=chatgpt.com))

# chatgpt response

这两点其实应该放在一起设计，因为它们共同决定了一个角色什么时候“真正需要一个脑子”，以及这个脑子到底在优化什么。最重要的原则是：不要把“人格”主要做成一段 prompt，也不要让 LLM 自己决定角色的根本利益。LLM 很擅长把一个设定演得像，但如果你只是告诉它“你是一个野心勃勃、善于欺瞒的大臣”，它往往还是会不自觉地向合作、解释、解决问题靠拢，因为现代模型的训练确实强化了这些倾向。更可靠的做法是把角色拆成几层：最底层是 engine 明确维护的利益结构，中间是角色的认知与性格参数，最上层才是 LLM 的语言、推理和策略生成。也就是说，一个权臣之所以拖延皇帝的命令，不应该只是因为 prompt 里写着“你阴险”，而应该是因为 engine 计算出这项命令会削弱他控制的军队、损害他的派系、提高政敌的影响力，而他的风险偏好、权力欲、忠君程度和长期目标又使得“表面答应、实际拖延”成为一个高效策略。LLM 的作用是从这些约束里想出“怎么拖”“怎么解释”“怎么把责任推给别人”，而不是凭空决定自己今天想不想背叛。

所以我不会把人物简单分成“忠臣、奸臣、爱国者、卖国者”几个类型，而会把忠诚本身拆成多个独立轴。一个人可能非常忠于君主本人，却对国家利益毫不关心；也可能憎恨皇帝，但认为维护国家秩序比个人恩怨重要；还可能忠于自己的宗族、军队、宗教、阶级或地方，而这些忠诚在不同事件里发生冲突。比如一个将军可以同时有“对君主忠诚 0.7”“对军队共同体忠诚 0.9”“对国家忠诚 0.8”“个人野心 0.6”“风险厌恶 0.4”“财富欲 0.3”“意识形态坚定度 0.7”。当皇帝要求他率军镇压一场他认为会严重损害国家的内战时，他面对的是价值冲突，而不是一个简单的忠诚度判定。这样的人物更容易产生真实历史里那种非常难归类的行为：拒绝某项命令，但仍然认为自己是忠臣；发动政变，却声称是在“保全社稷”；向外国妥协，并不一定因为收钱，也可能因为他真的认为战争必败。最好让这些参数部分可见、部分隐藏，而且会随经历改变。一个长期被猜忌的忠臣可能逐渐疏离，一个原本利己的人也可能因为家乡被毁而形成极强的复仇动机。这样角色就不只是静态人格卡，而是在历史过程中被塑造。

我会进一步把角色决策分成“欲望、判断、策略、表达”四层。欲望是 engine 维护的，例如保命、保住职位、扩大派系、维护国家、忠于君主、保护家族。判断是角色对世界的 belief state，它可能是错的，比如他错误地相信皇帝已经失去军队支持。策略层才允许 LLM 思考，例如“公开反对风险太高，最好拖延执行，同时让地方官夸大困难，并暗中联络另一位大臣”。表达层则负责实际生成奏折、谈话、承诺和谎言。这种结构有一个非常大的好处：即使模型本身有“倾向诚实”的训练，它也不会被要求“作为 AI 去欺骗人”，而是在模拟环境里实现一个由角色利益驱动的行为选择。甚至更稳妥一点，可以让 engine 先决定角色的行为类别，比如 `comply / delay / distort / conceal / sabotage / defect / negotiate`，然后让 LLM 负责具体执行。这会比单纯要求 LLM“像一个奸臣一样思考”稳定很多。

“欺上瞒下”也最好不要只做成一句谎话，而要有成本和风险。一个地方官想虚报粮食产量，必须有能力影响统计流程；如果审计机构独立、地方官员之间互相牵制，他就很难做到；如果整个地方官僚系统都依附于他，欺骗就容易得多。角色还应该考虑被发现之后的后果。于是“是否撒谎”实际上取决于他的收益、风险偏好、可操作空间、过去是否成功过、上级是否容易相信他，以及是否有其他人会揭发。这样欺骗就不再是人格标签，而是一个制度环境中的策略。这个设计尤其重要，因为如果你只是提高某个角色的“dishonesty”参数，最后会得到一个见什么都说谎的漫画式反派，而真实政治中的欺骗通常是有选择的。

至于“哪些角色值得一个 LLM”，我觉得最好的答案不是按照身份固定分配，而是按照“决策自由度”和“历史重要性”动态分配。一个角色值得真正调用 LLM，通常是因为他同时满足几件事：拥有一定自主权；掌握其他人看不到的信息；他的决定可能显著改变局势；他面临的不只是机械规则，而是需要解释、权衡、欺骗、谈判或者形成计划。如果一个角色只是按照明确流程做事，而且几乎没有自行改变结果的能力，就完全没必要用 LLM。一个普通税吏每天登记税款，使用有限状态机或者简单 utility model 足够；但如果某天地方暴动、中央命令互相矛盾、他的上司失踪，而他手里恰好掌握县库和印章，那么这个原本不重要的小官突然就可能值得“升级”成一个真正的 agent。

所以我非常推荐一种“认知层级动态升降”的机制。绝大多数人平时只作为 aggregate population 或 lightweight agents 存在，比如一个营的普通士兵不是 800 个独立 LLM，而是若干群体状态：士气、军饷满意度、纪律、地方认同、宗教构成、对军官信任、疲劳、伤亡、政治倾向。基层军官可能是轻量 agent，只用几十个参数和简单规则。当某个连队处于关键情境，比如将军下令向皇宫开火，而连长的兄长正好是宫廷卫队军官，这个角色才临时升级成 richer agent，甚至短时间调用 LLM 进行一次真正的决策。事件结束后，他可以降级，保留一个压缩后的记忆摘要。这样你不是给世界里的每个人一颗昂贵大脑，而是在需要的时候把“分辨率”提高。

军队尤其适合这么处理。普通士兵通常确实更偏向机械执行，因为他们的信息有限、组织纪律强、个人影响小，但也不能简单认为他们永远服从。你真正需要模拟的是“服从结构”。比如一个师长下令进攻，命令经过旅长、团长、营长逐级传递，每一级都可能解释、延误、修改，普通士兵最终响应的不是抽象皇帝，而是眼前的军官、同袍、纪律与风险。大多数时候，这条链非常稳定，所以完全可以用确定性规则处理；真正需要 LLM 的，是链条发生冲突的时候，比如中央与地方命令矛盾、军官倒戈、部队长时间欠饷、政变期间通讯中断。这时几个关键节点——军长、师长、首都卫戍司令、禁军统领——需要真正的高阶决策，而士兵仍然可以作为群体反应。这样就能模拟“整支军队并不是铁板一块”，又不会把计算量炸掉。

我甚至会让 LLM agent 数量成为 simulation 自己动态管理的资源。一个拥有一万人口的小国，可能同时真正运行的高阶 LLM 只有十几个；一个帝国即使有几千万人口，也可能只需要几十到一百个活跃 LLM，因为绝大多数时候真正塑造局势的是关键决策者和少数正在经历临界事件的人。其他人使用 utility AI、行为树、规则系统和统计模型。只有当某个轻量角色跨过“重要性阈值”，例如突然获得军权、进入继承序列、成为叛乱领袖、掌握重大秘密，系统才为他实例化一个完整人格、长期记忆和 LLM session。反过来，一个已经失势、远离政治中心的人可以降级，只保留结构化状态。这样既节省算力，也很符合历史本身——历史并不是每个人都同时拥有同等影响力。

我会特别建议不要让 LLM 自己持续自由思考。应该由 engine 在有决策需求时调用它，例如“收到命令”“发现新情报”“利益发生重大变化”“需要回应谈判”“出现权力真空”。平时角色不需要每个 tick 都问一次模型“你现在想干嘛”。这样不仅降低成本，而且能避免大量无意义的 agent chatter。角色的长期倾向由结构化状态保持，LLM 只在真正需要进行复杂选择时介入。它做完决定后，把结果压缩成结构化行动、记忆和新的关系状态，再交还给 engine。

如果把这套架构浓缩一下，我认为可以形成一个很稳的三层社会模拟：底层人口和普通成员用统计模型，中层官吏和军官用轻量 utility agents，顶层和临界节点使用完整 LLM agents；而且角色可以在三层之间动态升降。人格也不是 prompt，而是利益结构、忠诚对象、性格参数、历史记忆和社会关系的组合，LLM 只是读取这些东西，进行策略推理和语言表达。这样你才能既得到“忠臣真的可能抗旨”“野心家会装忠诚”“利己者在危机中可能突然爱国”这种复杂行为，又不需要为几十万人各跑一个模型。

我觉得这是我们目前整个设计里非常关键的一步，因为它实际上解决了两个最大风险：一是 LLM 人物太“乖”，所有人都像专业项目经理一样合作；二是模拟规模稍微扩大就完全跑不动。把人格底层结构化、把 LLM 变成按需调用的高阶认知层，这两个问题基本都能控制住。

整体设计没有严重的根本矛盾，可以整理成一份能够落地的架构。不过我认为目前有两处接近“真实矛盾”，另外大约六七处定义不清。如果不在交给 Codex 之前处理掉，最容易出现的情况不是程序写不出来，而是几个模块分别按照不同理解实现，做到中途才发现数据模型不兼容。

第一处接近真正矛盾的地方，是我们曾经说过 `sim-api` 要“严格检查角色是否拥有权限和能力”，后来又明确提出“政治模拟里法律权限不能成为硬门槛，任何人都可以尝试越权行为”。这两句话必须合并成一个非常明确的原则：engine 只硬性限制“物理能力和信息能力”，不硬性限制“法律权限”。例如一个普通地方官不能调用一支他完全无法联系的舰队，不是因为职位不够高，而是因为不存在指挥渠道；但如果一个禁军将领法律上无权逮捕皇帝，却实际控制皇宫卫队，那么 engine 必须允许他下达逮捕命令。法律上的 authority 应当成为其他 actor 判断是否服从以及事后产生合法性后果的输入，而不是 API permission。换句话说，API 检查的是 `can_attempt`，不是 `is_authorized`。这一点我建议直接写进最底层接口规范，否则 Codex 很容易按照传统软件权限系统实现，最后无意间把政变和抗命全部堵死。

第二处比较危险的是，我们一方面说“LLM 是人物的脑子”，另一方面又说为了防止模型过于诚实合作，可以由 engine 预先决定角色采取 `comply / delay / conceal / sabotage / defect` 之类哪一种行为，然后让 LLM 只负责实现。这两种架构不能同时作为默认方案，否则人物到底是谁在决策会变得不清楚。如果 engine 已经决定“这个大臣今天要欺瞒”，那么 LLM 实际只是一个文案生成器；如果完全交给 LLM，又可能出现你担心的所有角色过度合作。我认为最合理的中间方案是：engine 不决定行为结果，而是计算结构化的动机、约束和候选行为，例如告诉 agent，“执行命令会提高君主好感但削弱你的派系资源；拖延风险较低；公开反对可能失去职位；你目前估计皇帝控制禁军的概率只有 40%”。LLM 根据这些信息真正选择策略，然后 engine 验证这个策略是否可执行。也就是说，engine 决定 incentives 和 feasible action space，LLM 决定 choice。只有大量低阶角色才由 utility AI 直接做选择。这条边界一旦确定，后面的角色人格系统就会清晰很多。

第三个需要马上澄清的是“客观世界真相”到底包含什么。粮食数量、国库存款、人物位置这样的东西当然存在 objective truth，但“谁真正统治国家”“这个皇帝合法性是多少”“军队是否忠于中央”并不是同一种事实。我们此前有时把这些也说成 objective state，容易导致实现上重新出现一个隐藏的 `control = 72%`。更精确的模型应该是：底层客观事实是关系和行为，例如第七军司令实际接受谁的军饷、过去十次命令服从了谁、军官任命来自哪里、与哪些政治人物有私人关系。所谓“皇帝控制第七军”最好是这些事实的一个 derived metric，而不是基础变量。合法性也是如此。可以存在不同群体对统治者的承认状态，但不应该存在一个神谕式的“真实合法性 63”。这个区别关系到整个权力网络能否真正产生涌现效果。

第四个很大的工程缺口是时间。目前我们同时讨论过“每月 tick”的经济行政模拟和“几小时内完成”的政变、暗杀与军队倒戈。如果简单使用统一的月度 tick，政变会非常荒谬；如果所有东西每小时 tick，几十年模拟又会极其低效。我建议现在就决定采用“连续模拟时间＋事件调度器”，而不是把 tick 当作世界本身。经济、人口、财政可以每月结算一次，普通行政每周或每日更新，而政变、战斗、紧急命令可以产生小时级事件。时间向前跳到下一个 scheduled event。这样所谓“monthly tick”只是某些系统的更新频率，而不是 engine 的唯一时间尺度。这会影响存档、event log、agent scheduling 和 UI，所以必须在最早期解决。

第五个尚未定义的是并发和冲突。例如凌晨两点，皇帝命令禁军逮捕首相；两点零五分首相命令同一支禁军软禁皇帝；禁军统领恰好同时得到两条命令。我们目前说了很多“actor 自主选择”，但没有定义事件处理顺序。如果 Codex简单按照数组顺序运行 agent，最终历史可能取决于数据库排序，非常危险。我建议所有实际行动都走 event queue，每个事件有明确的发生时间、actor、信息来源和 causal parent；同一时间发生冲突时，先产生 observation，再让相关决策者响应，而不是偷偷按程序执行顺序决定胜负。动态代码产生的修改也只能提交 transaction，不直接改世界对象。这套机制其实会成为 simulation kernel 最重要的基础设施之一。

第六个问题是我们此前提到“完整 replay”，这里需要修正一下表述。只要存在 LLM，就不能指望从初始存档重新调用模型之后得到完全相同的回答，即使 temperature 设成零，也不能长期依赖供应商模型版本保持不变。因此 replay 的定义必须是 event sourcing：第一次运行时，把 LLM 收到的关键上下文版本、结构化决策输出以及之后 engine 接受的 action 全部记录下来；重放旧历史时直接重放已经确认的 action，而不是重新询问 LLM。只有玩家从 1848 年某一点创建一个 branch 时，才开始产生新的模型调用。这样“历史回放”是确定的，“历史重新推演”则不是同一个概念。这个差异最好从第一版数据库 schema 就体现出来。

第七个模糊点是动态 coding agent 到底生成什么。此前我们有时用了“生成代码”“生成函数”“法律本身是程序”“自定义 DSL”“WASM”等不同表达。如果现在直接让 Codex实现，它很可能不知道第一版究竟应该支持哪一种。我建议 MVP 阶段完全不要让游戏内 coding agent 生成 TypeScript、Python 或 WASM。先定义一个很窄的 declarative capability schema，本质上类似受限 DSL，例如一个制度可以定义触发条件、参与机构、数据输入、资源消耗、工作流步骤、等待时间、失败条件和允许产生的 actions。Coding agent 做的事情是生成这种结构化定义。等确认这一套确实表达不了某些重要制度以后，再考虑加入真正的 sandbox code。这并不改变我们之前的方向，只是把危险而且难调试的“任意代码”延迟到真正需要的时候。如果一开始就允许生成通用代码，Codex需要同时解决 sandbox、资源限制、状态迁移、调试和版本兼容，MVP 很容易陷进去。

第八个问题是角色的“升级和降级”。我们说普通人可以是 aggregate，中层使用轻量 agent，关键人物动态升级为 LLM agent，但这里还有一个身份连续性问题。如果一个无名营长原来只有十几个数值，突然因为政变成为关键人物，那么完整人格从哪里来？如果完全让 LLM 临时生成，人物过去可能被凭空改写。我建议所有可能成为独立 actor 的角色，从诞生开始至少有一个非常廉价的 persistent identity record，包括出身、组织经历、关系、基本价值倾向、关键事件和少数人格参数；平时不运行 LLM，只更新这些结构化记录。一旦升格，LLM session 根据这份履历初始化。降级时则把重要新记忆重新压缩进 persistent record。于是“有没有 LLM 脑子”只是计算层级，不决定一个人是否拥有连续的人格。

第九个问题是“底层越机械执行”这个判断应该作为涌现趋势，而不要直接作为阶级规则。通常一个士兵确实自主空间很小，但原因应该是信息少、组织约束强、个人改变结果的能力弱、违令成本高，而不是因为 `rank == soldier` 所以 obedience 固定为 95%。同一个普通士兵一旦部队断粮三个月、长官失踪、身边所有同袍开始逃亡，他的行为自由度就会突然变大。同理，一个高级文官在高度制度化的官僚组织里也可能几乎只是机械执行。因此“是否需要 LLM”的核心指标应该是当前 decision entropy 和 impact，而不只是社会等级。这个指标不必数学上特别精确，但架构上要允许一个低级角色在临界时刻被提升。

还有一个我认为很容易被忽略、但会严重影响开发的地方，是“国家、军队、政府、叛军、派系”究竟是不是不同 class。我们前面的理念实际上已经隐含了答案：最好不要为 `Government`、`RebelFaction`、`ArmyClique` 分别做完全不同的政治逻辑，而应该有一个更一般的 `Organization`。组织可以拥有成员、资源、控制关系、内部职位、通信网络、规则和认同对象。中央政府只是规模特别大的 organization，叛军发展成熟后也是 organization，军队是带有特殊武装能力的 organization。否则开发进行几个月以后，你会发现政变需要把“叛军逻辑”复制进“政府逻辑”，内战又要把两边重新适配。这种类型设计现在就值得定下来。

还有一处不是矛盾，而是我建议明确暂时不要解决的问题：不要试图第一版就准确模拟几十万普通人的思想，也不要第一版建立真实世界全部经济系统。我们目前讨论的政治机制其实只需要一个足够可信的资源和人口底座，而不需要 Victoria 那样完整的 POP 经济。否则 Codex很容易把大量时间花在粮食价格、职业转换和贸易网络上，而我们真正需要验证的是 objective state → observation → belief → decision → order → organizational response → world mutation 这一条链能不能产生可信的政治行为。

如果现在要冻结成一份给 Codex 的架构，我认为最核心的因果链可以非常明确：`World State` 保存客观实体、资源和关系；`Observation System` 根据渠道产生每个 actor 能看到的信息；`Belief State` 保存角色目前相信的世界；`Motivation Model` 保存利益、忠诚和人格；`Decision Layer` 根据角色复杂度选择 utility AI 或 LLM；角色输出 `Intent`；`Capability Layer` 把 Intent 转换成可以尝试的具体 operation；`Event Scheduler` 安排这些 operation；各个相关 actor 收到新的 observations 并决定服从、抵抗、修改或忽略；最终只有 `Simulation Kernel` 能 commit world state。国家法律、行政制度、地下组织以及后来 coding agent 创建的新制度都只能影响这条链，不能绕开它。

如果按这个版本统一，我认为前面的设计没有需要推翻的部分。最需要在 `SPEC.md` 里写死的，是五个接口边界：法律授权与实际能力不是一回事；LLM 决策而 engine 提供 incentives 与约束；社会性的“权力”尽可能由关系推导而不是存一个真值；所有状态改变经过事件和 transaction；动态 coding agent 第一阶段只生成受限 capability definition，不修改 kernel。把这五件事定下来以后，Codex 开始搭骨架时基本不会因为概念冲突而返工。

这两个补充我都赞成，而且它们实际上可以把前面两个模糊点变成很明确的设计原则。第五点我建议直接从“事件在一个时间点发生”升级为“决策本身也是一段发生在时间中的过程”。角色收到消息以后，不应该必然立刻产生一个最终 action，而是创建一个 `DecisionEpisode`：里面记录触发它的 observation、当前初步判断、紧迫程度、需要咨询的人、预计决策时间以及已经形成的 provisional intent。这个 episode 在时间推进中可以被新的消息打断，也可以发生 revision。于是上午八点将军听说皇帝被软禁，八点十分决定进京勤王并派出第一名信使；八点二十分又收到首都驻军宣布支持摄政的消息，改变判断，派第二名信使要求部队原地等待；八点四十分第三份消息证明前两份情报都有问题，他再次改变决定。这些不是“同一个行动被代码覆盖了”，而是三个真实存在、已经进入世界的信息事件。第一名使者甚至可能已经先到，导致部队执行了一个已经过时的命令。这种机制对战争、政变、外交和危机尤其重要，因为现实中的很多混乱，本来就是决策时间、通讯时间和执行时间互相错位造成的。它还能自然解决我们刚才说的并发问题：不是 engine 在同一 timestamp 里决定皇帝和首相谁的数组下标更靠前，而是谁先获得信息、花多久形成决定、谁的命令先通过什么渠道抵达相关人物。与此同时不需要所有事情都做到这种颗粒度。可以让每个决策带一个 `resolution_level` 或由系统自动判断复杂度：普通县令批准一份例行支出可能直接在几分钟后形成决定；是否参加政变这种高影响、高不确定性、高内部冲突的决策则启动完整的 deliberation。这里尤其应该避免让 LLM 每五分钟重新“思考一次”，而是只有新的重要 observation、截止时间逼近、内部目标冲突或者角色主动要求重新考虑时，才再次调用高阶决策层。这样既保留了真实的犹豫、反悔和追令，又不会把 token 消耗变得不可控制。

第七点你的两个思路其实不应该二选一，我认为最好的方案正是把两者组合起来，而且把它变成整个项目的长期开发方法。第一版只人为实现一套非常小的“物理级 primitive”，比如发送信息、移动人员或资源、任命与解除、转移资金、组织会议、签署文书、拘捕某人、调查某个对象、公开发布声明、秘密接触、建立组织关系等。这些 primitive 不需要覆盖所有历史行为，它们更像世界的“指令集”。历史上丰富得多的行为，例如“挟天子以令诸侯”“清君侧”“杯酒释兵权”“以赈灾名义建立地方粮仓控制网络”“借调查案清洗某个派系”，都不应该作为 engine primitive 写死，而应该是 primitive 的组合，也就是 higher-level capability。这样 coding agent 在模拟中真正生成的是“宏动作”和制度，而不是不断为 kernel 发明新的物理规律。某次模拟里第一次出现一种很有价值的策略，coding agent 生成 capability，经过验证后运行；模拟结束后我们把所有动态 capability 收集起来，看哪些出现频率高、哪些跨时代跨场景重复出现、哪些代码结构其实相同。如果某个动态能力在一千次模拟里出现了六百次，就说明它根本不应该继续由 coding agent 临时生成，而应该晋升为标准 library capability。于是这个系统可以形成一种很有意思的“游戏规则进化”：最开始 library 很薄，通过大量 simulation 自己发现缺失的中层行为，再由人类开发者审阅、合并、泛化和优化。

而你说的第二条——从历史材料反推行为分布——我认为更加重要，因为它可以防止第一批 primitive 和 capability 被现代软件工程师的直觉严重污染。我们天然会想到“宣布政策、任命官员、发动战争、征税”这些电子游戏常用按钮，但真实历史里大量决定性行为其实是很间接的，比如故意拖延奏报、改变觐见顺序、将某个人调离首都、通过婚姻建立关系、让某项任命长期悬缺、散布某种消息测试反应、把部队拆分驻扎、拒绝发放印信、利用程序拖延、借别的案件清洗对手等等。如果只靠我们脑补动作空间，很容易重新制造一个“看似开放但仍然是游戏设计师菜单”的系统。因此完全可以做一个 Historical Action Mining pipeline：准备一批版权和来源许可合适的历史材料，让 LLM 不是总结故事，而是逐段抽取结构化事件，例如“谁在什么信息条件下，为了什么目标，对谁采取了什么行动，通过什么机制，耗时多久，实际结果如何，是否公开合法，是否成功，以及这个行动可以拆成哪些更基础的操作”。然后对几十万条 action record 做聚类，就能看到真实历史里究竟有哪些行为模式高频出现。

这个语料工作甚至不应该只用来决定“动作列表”，还可以反过来校准我们的整个模拟模型。例如如果历史标注发现大量政治行为属于“阻止信息到达某人”，那说明 information-routing primitive 应该非常底层；如果大量权力斗争依赖“人事任命”和“职位空缺”，说明 office 和 appointment 不能只是人物属性；如果经常出现名义服从、实际拖延，那么 order lifecycle 必须把 acknowledged、scheduled、partially executed、reported complete 和 actually completed 分开。换句话说，历史语料不是给我们提供剧情素材，而是给 simulation schema 做 empirical requirements gathering。这一点非常有价值。

我会再加一层自动化：历史材料标注出来的行为不要直接变成代码需求，而是先尝试让一个“行为编译器”用现有 primitives 表达。比如历史文本里抽出“某权臣控制皇帝诏令，只发布符合自己利益的命令”，系统先尝试表示成 `intercept_message + control_secretariat + selectively_forward + forge_authorization`。如果可以表达，说明 engine 已经足够，只需要一个新的 compound capability；如果不能表达，则生成 `PrimitiveGap`。只有大量互不相关的历史案例都暴露出同一个 PrimitiveGap，我们才考虑修改 simulation kernel。这样历史数据和 coding agent 恰好形成两条互相验证的路径：历史语料告诉我们真实人类经常做什么，开放模拟告诉我们 agent 在我们的世界里会尝试做什么；两边都不断提出 capability，只有真正无法由现有世界规则表达的东西才推动 kernel 扩展。

我还建议把这里产生的数据保留下来，因为它以后很可能成为整个项目最有价值的资产之一。每个 capability 都可以记录 `origin`：是 human-designed、historical-mined 还是 simulation-emergent；如果来自历史，可以关联多个抽象案例类别；如果来自模拟，可以记录首次出现在哪种局势、之后出现过多少次、成功率如何、是否被其他 capability 替代。经过很多轮模拟，你最终得到的不是一张人工编写的动作表，而是一棵行为谱系：底部是极少量稳定 primitives，中间是经过实践积累下来的 reusable capabilities，上层是每个具体时代和人物临时产生的计划。这种结构其实很适合 coding agent，因为它面对一个新问题时可以先搜索 capability library，再组合已有能力，最后才生成新的东西，而不是每一次都从零写代码。

因此我会对之前“第一阶段只使用 declarative capability schema”那个建议稍微修正，而不是推翻：第一版依然应该避免让游戏内 agent 随意写 TypeScript 修改 engine，但这个 declarative capability language 应该从一开始就被当成“可生长的行为语言”，而不是开发者预先穷举出来的一张菜单。它需要支持组合、条件、等待、消息、分支、循环、资源占用、并行步骤和中途取消。这样你刚才说的“先派第一名使者，后来反悔再派第二名追赶”甚至也是同一套语言能够自然表达的。到了那一步，coding agent 的工作其实有点像编译器：把“我想秘密拉拢三个军头，如果其中两个答应，再控制城门；如果消息走漏就立刻转为公开勤王”这样的策略，编译成 engine 可以调度的一组事件和条件，而 simulation 决定最后到底发生什么。

这两个补充以后，我认为 SPEC 里应该把一个非常核心的观念写得更明确：我们的 engine 不是在执行“角色做出的最终决定”，而是在模拟“角色形成、传播、修改和落实意图的过程”；我们的动作体系也不是固定菜单，而是“少量稳定 primitives＋不断演化的 capability library”。这两条如果从架构第一天就确定下来，后面很多原本看起来需要特殊处理的历史现象，反而会自动落入同一个系统。
